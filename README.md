## 5. Стратегии слияния

В работе использованы три способа слияния.

**Fast-forward.** Если `main` не двигался с момента ответвления, Git просто
переносит указатель вперёд. Отдельный merge-коммит не создаётся, история
остаётся линейной.

**Merge-коммит (`--no-ff`).** Создаётся коммит с двумя родителями: `main` и
веткой. В истории видно, где именно ветка вошла в `main`. Это удобно, если
ветка уже опубликована и важно сохранить контекст.

**Rebase.** Коммиты ветки переносятся на новую вершину `main`, их хеши
изменяются. После этого возможен fast-forward. Rebase уместен для личной ветки,
которую ещё никто не тянул; для опубликованной ветки он опасен, потому что
переписывает общую историю.

| № | Ветка | Коммит(ы) | Что принесла | Стратегия | Обоснование |
|---|---|---|---|---|---|
| 1 | `arsen/modules` | `949f2e4` | «Модули и пакеты» | fast-forward | `main` не двигался, ветка была ровно на один коммит впереди. Перемотка не создаёт лишний merge-коммит. |
| 2 | `arsen/git` | `2bc647b` → `430aaba` после rebase | «Ветки и конфликты» | rebase + fast-forward | Ветка личная, её ещё никто не тянул. Rebase дал линейную историю. Хеш изменился; ветка ещё не была опубликована, поэтому на GitHub ушёл уже новый хеш. Для уже опубликованной ветки понадобился бы `git push --force-with-lease`. |
| 3 | `roma/matplotlib` | `8d5e960` → merge `a53a8d5` | «Практикум matplotlib» | merge `--no-ff` | Ветка уже была на GitHub. Переписывать её историю после push нельзя. Merge-коммит фиксирует факт слияния. |
| 4 | `roma/missing` | `7f911b5` → merge `93fd35e` | «Пропуски и дубликаты» | merge `--no-ff` | Ветка опубликована, история не переписывается. Merge-коммит показывает границу работы Ромы. |
| 5 | `arsen/outliers` | `bd6d715` → merge `dca7d31` | «Выбросы, типы, унификация» | merge `--no-ff` | Большой ноутбук на 80 ячеек. Merge-коммит оставляет видимую точку входа. |
| 6 | `roma/outliers` | `4e8a426` → merge `55d89bd` | Тот же путь, вариант Ромы | merge `--no-ff` + разрешение конфликта | Обе ветки добавили один и тот же путь. Git выдал `CONFLICT (add/add)`. Файл собран вручную. |

Почему стратегии разные:

- fast-forward использован там, где `main` ещё не двигался;
- rebase — только для личной ветки, чтобы не переписывать опубликованную историю;
- merge-коммиты — для веток, которые уже были на GitHub и/или требовали
  сохранения контекста.

## 6. Разрешение конфликта

Оба участника добавили файл с одним и тем же путём:

```text
notebooks/05-outliers/Выбросы_типы_унификация.ipynb
```

В ветке Арсена было одно решение, в ветке Ромы — другое. При слиянии Git выдал:

```text
CONFLICT (add/add): Merge conflict in notebooks/05-outliers/Выбросы_типы_унификация.ipynb
```

`git status` показал `AA`: обе стороны добавили файл. Конфликт разрешён вручную:

1. Оба JSON открыты и сравнены по ячейкам. Ноутбуки совпали везде, кроме пяти
   ячеек с решениями задач 1–5.
2. За основу взято решение Арсена: оно осталось в основной части ноутбука и
   используется всеми проверками.
3. В конец файла добавлено приложение «Варианты решения Ромы» с пятью
   альтернативными функциями. Так в одном файле видны оба подхода, а ноутбук
   остаётся исполнимым: приложение идёт после проверок и ничего не меняет.
4. Файл проверен командой:

   ```bash
   python3 -m json.tool "notebooks/05-outliers/Выбросы_типы_унификация.ipynb" > /dev/null
   ```

   Команда ничего не напечатала, значит JSON корректен.
5. Проверено, что выводы очищены: `outputs` пустые, `execution_count` равен
   `null`.
6. Слияние завершено:

   ```bash
   git add "notebooks/05-outliers/Выбросы_типы_унификация.ipynb"
   git commit --no-edit
   ```

В `main` остался один файл. Внутри — решение Арсена и варианты Ромы для задач
1–5. Файлов вида `Выбросы ... (1).ipynb` нет.

Отличия решений:

| Задача | Арсен | Рома |
|---|---|---|
| 1. Часы из текста | Одно регулярное выражение `часов|часа|ч` | Три последовательных `str.replace` |
| 2. Анкеты по дням | `groupby(...).count()` | `value_counts().sort_index()` |
| 3. Любимый предмет | `map` и `lambda` | `Series.replace(SUBJECTS)` |
| 4. Невозможные значения | Маска и копия столбца | `Series.where` |
| 5. Границы выбросов | Промежуточные переменные | Компактная запись одной строкой |

## 9. Выводы

- Ветка — это указатель на коммит, а не копия папки. Создание и удаление ветки
  не требует копирования файлов.
- Fast-forward, merge и rebase решают разные задачи. Перемотка упрощает
  линейную историю, merge сохраняет контекст, rebase делает историю линейной,
  но переписывает хеши.
- Опубликованную ветку не следует ребейзить без необходимости: это меняет
  общую историю.
- Конфликт в JSON-файле разрешается редактированием содержимого, после чего
  файл нужно проверить через `python -m json.tool`.
- После каждого слияния `main` должен оставаться рабочим: ноутбуки
  открываются, JSON корректен, выводы очищены.
